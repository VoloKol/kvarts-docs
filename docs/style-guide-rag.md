## 1. Как RAG читает документацию

RAG (retrieval-augmented generation, «генерация, дополненная поиском») — архитектура ассистента, который отвечает на вопросы по базе знаний. Работает он так: на вопрос пользователя система ищет в индексе фрагменты текста, похожие на вопрос, передаёт найденное языковой модели, и модель собирает из этих фрагментов ответ, указывая, из каких статей он собран.

Из этого устройства следуют четыре факта, на которых построен весь стайлгайд:

1. **Единица поиска — не статья, а чанк (chunk, фрагмент).** Пайплайн нарезает статьи на фрагменты, обычно по границам заголовков. Типичный чанк — раздел размером от 200 до 800 токенов; более длинные разделы режутся дальше, иногда посреди абзаца.
2. **Модель видит чанк отдельно от статьи.** Соседние разделы, оглавление и оформление к чанку «не приезжают»: у него есть только собственный заголовок и метаданные статьи.
3. **Ассистент отвечает тем, что нашёл.** Если найденный фрагмент непонятен сам по себе или не содержит полного ответа, ассистент отвечает невпопад (галлюцинация) либо отказывается отвечать — даже если правильная статья в базе существует.
4. **Находится фрагмент, чей текст ближе всего к формулировке вопроса.** Пользователь спрашивает «не приходит письмо со сбросом пароля» — релевантен раздел, написанный этими же словами, а не раздел «Особенности почтовых уведомлений».

Хорошая для RAG статья обладает тремя свойствами: **самодостаточность** (каждый раздел честно отвечает на вопрос без соседей), **однозначность** (один термин — одно понятие), **находимость** (лексика статьи совпадает с лексикой пользователей). Дальше — как этого добиться структурой, языком и разметкой.

## 2. Общие принципы

Шесть принципов ниже — основа, из которой выведены правила разделов 3–7. Если конкретное правило кажется спорным, вернитесь к принципу.

**2.1. Один тезис — один раздел.** Раздел посвящён одной мысли; если мыслей две — это два раздела. Почему: чанк, посвящённый одной теме, точнее находит по запросу и чище цитируется; смешанный чанк «про лимиты и заодно про пароли» проигрывает обоим тематическим конкурентам.

**2.2. Каждый раздел самодостаточен.** Тест: вырвите раздел из статьи и дайте коллеге без контекста — он должен понять и применить его без остальных разделов. Почему: ассистент получает чанк именно так — отдельно, без статьи вокруг.

**2.3. Один термин — одно понятие.** Выберите один термин («баланс» или «остаток на счёте») и держите его по всей статье; вторую лексику выносите в поле `tags` front matter. Почему: поиск сопоставляет слова вопроса со словами чанка; расхождение терминов между статьями снижает точность, а необъяснённый синоним — корректность ответа.

**2.4. Факты — в тексте, не в оформлении.** Важные условия, ограничения и шаги не должны существовать только в картинке, в ката с заголовком «Подробнее», в HTML-комментарии или в подписи скриншота без alt-текста. Почему: такое содержимое либо не попадает в индекс, либо попадает без контекста.

**2.5. Время и версии — абсолютные.** «С версии 3.4 (июнь 2026 года)», «с 12 марта 2025 года» — вместо «недавно», «в новой версии». Почему: чанк лежит в индексе месяцами и читается в будущем; относительные даты делают его неверным уже на следующий день.

**2.6. Сначала для человека, потом для ассистента.** Правила этого стайлгайда совпадают с правилами хорошей технической документации: структура, ясность, точность. Писать «специально для бота» не нужно — нужно, чтобы каждый фрагмент выдерживал тесты принципов 2.1–2.5.

## 3. Структура статьи

Чанки режутся по границам заголовков, поэтому структура — не вкусовщина, а механика поиска.

### 3.1. Заголовок H1

**Правило.** В статье один заголовок H1; он совпадает с полем `title` из front matter и является полным названием, понятным без статьи: не «Введение» и не «Обзор», а «Как сбросить пароль в веб-консоли».

**Почему.** H1 — главный сигнал релевантности: он приписывается каждому чанку статьи и первым попадает в ответ ассистента как название источника.

Плохо: `# Введение`. Хорошо: `# Как сбросить пароль в веб-консоли`.

### 3.2. Иерархия заголовков

**Правило.** Уровни идут без пропусков: H2 → H3 → H4. Каждый заголовок информативен сам по себе: прочитав только заголовки, читатель должен получить конспект статьи. Вопросы FAQ формулируются как настоящие вопросы пользователя.

**Почему.** По заголовкам пайплайн определяет границы и «адрес» чанка; пропуск уровня ломает дерево разделов, а заголовки-пустышки («Важно», «Шаги», «Продолжение») делают чанк ненайденным.

Плохо: `### Важно`. Хорошо: `### Как проверить, что лимит исчерпан`.

### 3.3. Лид статьи

**Правило.** Первый абзац — 1–3 предложения: что это за материал, для кого, какой результат даст. Ключевые слова, которыми пользователь описывает проблему, ставятся в первое предложение.

**Почему.** Первый абзац почти всегда становится чанком-представителем статьи: по нему система решает, относится ли статья к вопросу.

```markdown
Эта инструкция описывает, как сбросить забытый пароль веб-консоли
и восстановить доступ к аккаунту. Сброс занимает около пяти минут.
```

### 3.4. Абзацы

**Правило.** Абзац — 2–4 предложения об одной мысли. Первое предложение абзаца несёт суть, остальные раскрывают. Не растягивайте абзац на 300 слов и не дробите мысль на строки-однострочники.

**Почему.** Длинный абзац нарезается посреди мысли, а короткие строки-однострочники при нарезке приклеиваются к соседям и теряют самостоятельность. Первое предложение абзаца чаще всего «выживает» в чанке — несите в нём суть.

### 3.5. Списки и шаги

**Правило.**

- Списки — для однородных перечислений; вложенность — не глубже двух уровней.
- Связное объяснение не превращайте в список: если пункты нельзя переставить местами без потери смысла, это абзацы.
- Инструкции — нумерованные списки: один шаг — одно действие, в конце шага — ожидаемый результат.
- Шаг формулируется так, чтобы быть понятным и без соседних: где нажать, что ввести, что появится.

**Почему.** Пункты списков при нарезке и цитировании живут поодиночке. Шаг без результата («Настройте лимиты и проверьте всё») не даёт ассистенту материала для ответа.

Плохо: `3. Настройте лимиты и проверьте всё.`

Хорошо: `3. Установите лимит 100 RPS в разделе «Лимиты» — после сохранения появится статус «Применён».`

### 3.6. Таблицы

**Правило.** Перед каждой таблицей — подводка из одного предложения, содержащая главный вывод, а не отсылку вида «см. таблицу». Заголовки колонок — полные слова; единицы измерения — в шапке. В ячейках обычной таблицы — однострочный контент; многострочный (списки, код) — только в расширенной таблице YFM (см. раздел «Портал на Diplodoc»).

**Почему.** Таблицы при нарезке распадаются на строки; подводка с выводом и полная шапка сохраняют контекст каждой строки.

Хорошо: `Лимиты зависят от тарифа: базовый — 100 RPS, профессиональный — 1000 RPS.` — затем таблица с полной шапкой.

### 3.7. Картинки

**Правило.** У каждой картинки — alt-текст, описывающий смысл: «Схема распределения лимитов между проектами». Ключевые факты, существующие только на картинке, продублируйте текстом рядом.

**Почему.** В индекс попадает alt-текст, а не пиксели. Факт «только на скриншоте» для ассистента не существует.

### 3.8. Ссылки

**Правило.** Текст ссылки — осмысленный: название статьи или действие («см. раздел `[Лимиты запросов](limits.md)`»), а не «здесь», «тут», «по ссылке». Ссылки между статьями — относительные.

**Почему.** Текст ссылки попадает в чанк: «см. здесь» в ответе ассистента бесполезен и не работает как сигнал релевантности. Относительные ссылки остаются корректными при смене домена портала.

### 3.9. Частые вопросы

**Правило.** В конце статьи — раздел «Частые вопросы» с заголовками-вопросами в лексике пользователя; каждый ответ — 1–3 предложения и самодостаточен.

**Почему.** Вопросы пользователей почти дословно совпадают с вопросами-заголовками FAQ — это самый дешёвый способ получить точное попадание чанка.

## 4. Метаданные статьи (YAML front matter)

Front matter — блок YAML-метаданных между строками `---` в начале файла. Пайплайн индексации забирает его целиком и приписывает каждому чанку статьи: по метаданным работают фильтры поиска, витрина источников в ответах ассистента и сортировка по свежести. Статья без front matter считается непроиндексированной и в merge request не проходит.

### 4.1. Обязательная схема

| Поле | Обязательное | Формат | Пример | Зачем RAG |
|---|---|---|---|---|
| `title` | да | строка, совпадает с H1 | Как сбросить пароль в веб-консоли | главный сигнал релевантности, название источника в ответе |
| `description` | да | 1–2 предложения, не копия `title` | Пошаговый сброс пароля по ссылке из письма, ссылка действует 24 часа | сниппет источника в ответах ассистента |
| `article_id` | да | slug из латиницы и дефисов, уникален, никогда не меняется | reset-console-password | стабильная ссылка на источник, дедупликация статей |
| `product_area` | да | значение из утверждённого списка областей продукта | console | фильтрация поиска по продукту |
| `tags` | да | 3–7 фраз лексикой пользователя | пароль, вход, не могу войти | синонимы, которых нет в тексте статьи |
| `audience` | да | `user`, `admin`, `developer` или `all` | user | подбор ответа под роль спрашивающего |
| `status` | да | `draft`, `review`, `active` или `deprecated` | active | в индекс попадают только активные статьи |
| `updated_at` | да | ISO 8601, дата последнего фактического изменения | 2026-11-04 | свежесть и приоритет источников |
| `owner` | да | команда или ответственный | Поддержка L2 | адресат проверки актуальности |

### 4.2. Правила заполнения

- `title` совпадает с H1 посимвольно — расхождение ловит линтер (см. раздел «Автоматические проверки в MR»).
- `tags` заполняйте лексикой реальных обращений пользователей, а не внутренним жаргоном: расхождение синонимов — главный источник промахов поиска.
- `description` дополняет `title`, а не повторяет его; включайте в него ключевой факт (срок действия ссылки, ограничение).
- `article_id` не переиспользуйте: чанки предыдущей версии статьи ссылаются на него из индекса, переименованный id «рассыпает» историю источника.
- Пустых полей не оставляйте: незаполненное обязательное поле блокирует merge.
- Устаревшие статьи не удаляйте, а переводите в `status: deprecated`: они исчезают из индекса, но история ссылок сохраняется. Правила пометки устаревших статей — в регламенте репозитория.

### 4.3. Пример

```yaml
---
title: Как сбросить пароль в веб-консоли
description: Пошаговый сброс забытого пароля веб-консоли по ссылке из письма; ссылка действует 24 часа.
article_id: reset-console-password
product_area: console
tags:
  - пароль
  - вход
  - восстановление доступа
  - не могу войти
audience: user
status: active
updated_at: 2026-11-04
owner: Поддержка L2
---
```

## 5. Язык и формулировки

### 5.1. Аббревиатуры и термины

**Правило.** Аббревиатура при первом употреблении в статье раскрывается: «RAG (retrieval-augmented generation)». Корпоративный сленг и локальные сокращения в статьи базы знаний не попадают.

**Почему.** Чанки читаются независимо от глоссария, а модель может не знать внутренних сокращений — ответ будет построен на неверной интерпретации.

### 5.2. Синонимы

**Правило.** Одно понятие — один термин в рамках статьи. Вторая лексика допускается один раз в виде вводного синонима («чанк (фрагмент)») и в поле `tags`.

**Почему.** Чередование синонимов «для красоты» размывает релевантность каждого чанка: эмбеддинги (векторные представления текста) разных разделов расходятся, и статья ищется хуже.

### 5.3. Даты, версии, числа

**Правило.** Все привязки ко времени — абсолютные: «с версии 3.4», «с 12 марта 2025 года». Числа — с единицами измерения: «100 RPS», «24 часа», «30 дней». Диапазоны — явные: «от 2 до 8 проектов».

**Почему.** Чанк живёт в индексе дольше, чем статья «на портале»: относительные формулировки («недавно», «в новом релизе») устаревают в день публикации и делают чанк неверным.

### 5.4. Ограничения и отрицания

**Правило.** Ограничение формулируется явно и с альтернативой: «Подключить второй номер нельзя: повторная привязка снимает первый. Вместо этого используйте резервные коды». Размытые формулировки вида «не рекомендуется» без объяснения причины не используются.

**Почему.** Ассистент копирует формулировку источника: размытое ограничение превращается в размытый ответ, а необъяснённый запрет порождает следующий вопрос пользователя.

### 5.5. Никаких ссылок на порядок чтения

**Правило.** «См. выше», «см. ниже», «как уже упоминалось», «в предыдущем разделе» — запрещены. Вместо них — повтор ключевого факта одной фразой или полная ссылка с осмысленным текстом.

**Почему.** У чанка нет «выше» и «ниже»: соседние разделы не попадают в контекст вместе с ним. Такие обороты ловит линтер (см. раздел «Автоматические проверки в MR»).

### 5.6. Лексика пользователя

**Правило.** Заголовки, FAQ и `tags` пишутся словами пользователя: «Не приходит письмо со ссылкой для сброса», а не «Особенности доставки почтовых уведомлений».

**Почему.** Поиск сопоставляет вопрос пользователя с текстом чанка; чем ближе лексика, тем выше шанс попадания.

## 6. Портал на Diplodoc: YFM-разметка и RAG

Портал собирается движком Diplodoc из YFM (Yandex Flavored Markdown — диалект CommonMark с дополнительными элементами разметки). В контур RAG текст поступает после конвертации в HTML и извлечения текста, поэтому требование одно: содержимое каждого элемента должно превращаться в самодостаточный текст без потерь.

Раздел действует для статей портала. Если статья живёт только в базе знаний на чистом Markdown, интерактивные элементы YFM в ней не используются, а требования самодостаточности те же.

Общий принцип: интерактивные элементы (заметки, каты, табы) удобны читателю портала, но при нарезке превращаются в обычные чанки — «интерактивность» исчезает, остаётся текст и заголовок элемента. Пишите так, чтобы заголовок элемента работал как заголовок раздела.

### 6.1. Заметки

{% note info %}

Ссылка из письма действует 24 часа с момента отправки.

{% endnote %}

Типы заметок: `info` — дополнение, `tip` — совет, `warning` — важно, `alert` — опасно или запрещено. Можно задать свой заголовок: `{% note warning "Лимит по умолчанию" %}`.

**Правило.** Тип заметки соответствует смыслу; у значимой заметки — свой заголовок в одну строку; текст заметки полный и самостоятельный, без ссылок «см. ниже». Конструкция отделяется пустыми строками снаружи и внутри — иначе портал не обработает её и выведет сырой текст с тегами, и этот же мусор уйдёт в индекс.

**Почему.** Заметка становится отдельным чанком-«приложением»; её заголовок — единственный поисковый крючок этого чанка.

### 6.2. Каты (спойлеры)

{% cut "Доступные регионы: полный список" %}

- Россия: `moscow`, `spb`
- Казахстан: `almaty`
- Турция: `istanbul`

{% endcut %}

**Правило.** Заголовок ката — конкретная формулировка содержимого («Полный список регионов», а не «Подробнее»). В катах можно прятать справочные списки, длинные примеры и редко нужные детали. Нельзя прятать в кат то, что закрывает частый вопрос пользователя: такие ответы — в основной текст или в FAQ.

**Почему.** Для поиска кат — это чанк, представленный только своим заголовком: если заголовок «Подробнее», содержимое не найдётся никогда.

### 6.3. Табы

{% list tabs %}

- macOS

  1. Установите утилиту: `brew install example-cli`.
  2. Проверьте версию: `example-cli --version` — в терминале появится номер версии.

- Linux (deb)

  1. Скачайте пакет со страницы релизов.
  2. Установите: `sudo apt install ./example-cli.deb`.

{% endlist %}

**Правило.** Табы — только для альтернативных способов одного действия (операционная система, интерфейс, язык). Каждый таб — законченный вариант инструкции: открыв один таб, пользователь выполняет задачу целиком. Названия табов — конкретные («macOS», «Linux (deb)», а не «Вариант 2»).

**Почему.** Табы нарезаются независимо: инструкция, разорванная по табам («шаги 1–2 — в первом табе, шаг 3 — во втором»), даёт обрывки-чанки, каждый из которых бесполезен.

### 6.4. Таблицы

**Правило.** Простые таблицы — GFM-разметкой с пайпами (ячейки однострочные). Многострочное содержимое в ячейке (списки, код, переносы) — расширенными таблицами YFM:

```markdown
#|
|| Этап | Что проверяем ||
|| Подготовка |
- доступ к проекту
- роль `editor` ||
|| Запуск |
- лимиты квоты
- логи в консоли ||
|#
```

Подводка перед таблицей обязательна — см. раздел «Структура статьи».

**Почему.** GFM-таблица с переносом строки внутри ячейки разваливается при извлечении текста; расширенная таблица сохраняет принадлежность строк ячейкам.

### 6.5. Переменные и условия

Синтаксис:

```markdown
Подстановка: {{ имя_переменной }}
Условие:     {% if OS == 'iOS' %} … {% else %} … {% endif %}
```

**Правило.** Динамический контент допустим, только если подстановка гарантирована на этапе сборки портала. Требование к MR: в собранном тексте не должно оставаться недоподставленных переменных и неразрешённых условий — проверка входит в CI. Если обе ветки условия должны существовать в базе знаний как отдельные ответы, не прячьте их в условный вывод: собранный текст содержит только одну ветку.

**Почему.** Недоподставленная переменная попадает в ответ ассистента как есть:

```markdown
Настройте {{ лимит }} запросов
```

### 6.6. Комментарии

**Правило.** HTML-комментарии `<!-- ... -->` — только для служебных пометок редакторам («уточнить дату релиза»). Факты, правила и ограничения в комментариях не хранятся.

**Почему.** Комментарий либо выпадает из текста, либо попадает в индекс как мусор — в обоих случаях спрятанный факт для ассистента не существует или врёт.

### 6.7. Запреты на портале

- HTML-теги в тексте: YFM экранирует их по умолчанию, читатель увидит теги как текст — и на портале, и в чанках.
- Вложенность интерактивных элементов глубже одного уровня (кат внутри таба внутри ката): нарезка теряет структуру.
- Критичная информация (доступы к продакшену, схемы эскалации) только внутри ката или таба.

## 7. Автоматические проверки в MR

Автопроверки снимают рутину с ревью и не пускают «анти-RAG» паттерны в основную ветку. Стек: markdownlint-cli2 (структура разметки) и Vale (языковые правила). Конфиги лежат в корне репозитория; проверки запускаются локально перед push и в CI на каждый merge request. Merge блокируется, если есть ошибки уровня `error`; предупреждения — на усмотрение ревьюера.

### 7.1. markdownlint-cli2

Файл `.markdownlint-cli2.jsonc`:

```jsonc
{
  "config": {
    "default": true,
    // длина строки не ограничиваем: переносы не влияют на чанкинг
    "MD013": false,
    // одинаковые заголовки разрешены у разных родителей (FAQ в разных разделах)
    "MD024": { "siblings_only": true },
    // без HTML: YFM экранирует теги как текст
    "MD033": true,
    // без «жирного текста вместо заголовка»
    "MD036": true,
    // каждый код-блок — с указанием языка
    "MD040": true,
    // статья начинается с H1
    "MD041": true
  },
  "globs": ["**/*.md"],
  "ignores": ["**/node_modules/**"]
}
```

Правила, важные для RAG:

| Правило | Что проверяет | Зачем |
|---|---|---|
| MD001 | Скачки уровней заголовков | дерево чанков строится по заголовкам |
| MD025 | Один H1 на файл | единственный заголовок-представитель статьи |
| MD033 | HTML в тексте | экранированный тег — мусор в чанке |
| MD036 | Курсив или жирный вместо заголовка | потерянный заголовок — потерянный адрес чанка |
| MD040 | Язык код-блока | примеры ищутся и цитируются корректно |
| MD041 | H1 в первой строке | статья без названия не имеет представителя |
| MD042 | Пустые ссылки | ссылка-заглушка попадает в ответ как битая |
| MD047 | Файл кончается переносом строки | стабильные диффы в git |

### 7.2. Vale

Файл `.vale.ini`:

```ini
MinAlertLevel = error

StylesPath = styles

[*.{md}]
BasedOnStyles = KB
```

Правила собственного стиля `KB` (каталог `styles/KB/`):

```yaml
# styles/KB/AbsoluteDates.yml
extends: existence
message: 'Замените «%s» на абсолютную дату или версию: «с 12 марта 2025 года», «с версии 3.4».'
level: error
ignorecase: true
tokens:
  - недавно
  - вчера
  - сегодня
  - на прошлой неделе
  - на следующей неделе
  - в ближайшее время
  - в скором времени
  - в новой версии
```

```yaml
# styles/KB/NoContextReferences.yml
extends: existence
message: 'Чанки самодостаточны: уберите «%s», повторите факт или поставьте полную ссылку.'
level: error
ignorecase: true
tokens:
  - см. выше
  - см. ниже
  - как уже было сказано
  - как уже упоминалось
  - в предыдущем разделе
```

```yaml
# styles/KB/MeaningfulLinks.yml
extends: existence
message: 'Текст ссылки должен быть осмысленным: «%s» не описывает назначение ссылки.'
level: warning
ignorecase: true
tokens:
  - здесь
  - тут
  - по ссылке
  - по этой ссылке
```

Встроенная орфографическая проверка Vale рассчитана на английский и для русского текста не подключается: формулировки проверяют правила выше, а орфографию и терминологию — ревьюер и глоссарий (см. раздел «Глоссарий»).

### 7.3. Запуск

Локально перед push:

```bash
npx markdownlint-cli2 "**/*.md" "#node_modules"
vale --config .vale.ini .
```

Пример CI-задания (GitLab CI; для другой платформы адаптируйте команды):

```yaml
lint-structure:
  image: node:20
  script:
    - npx markdownlint-cli2 "**/*.md" "#node_modules"

lint-language:
  image: jdkato/vale:latest
  script:
    - vale --config .vale.ini .
```

## 8. Чек-лист автора перед MR

### Структура

- [ ] H1 один, совпадает с `title`, название полное (не «Введение»).
- [ ] Уровни заголовков без пропусков; из одних заголовков складывается конспект.
- [ ] Первый абзац отвечает: что это, для кого, какой результат.
- [ ] Абзацы — 2–4 предложения, суть — в первом предложении.
- [ ] Списки однородные, вложенность не глубже двух; инструкция — нумерованные шаги с результатом.
- [ ] У таблиц есть подводка с выводом и полная шапка.
- [ ] У картинок есть alt-текст; ключевые факты продублированы текстом.
- [ ] Тексты ссылок осмысленные, ссылки между статьями относительные.
- [ ] Есть раздел «Частые вопросы» с вопросами-заголовками.

### Язык

- [ ] Аббревиатуры раскрыты при первом употреблении.
- [ ] Один термин на понятие; вторая лексика — в `tags`.
- [ ] Даты и версии абсолютные; числа — с единицами.
- [ ] Ограничения сформулированы явно, с альтернативой.
- [ ] Нет «см. выше», «как уже упоминалось», «в предыдущем разделе».

### Метаданные

- [ ] Front matter заполнен целиком, форматы полей — из раздела «Метаданные статьи».
- [ ] `tags` — лексика пользователей, 3–7 фраз.
- [ ] `article_id` не менялся; `updated_at` проставлен; `status` актуален.

### Портал (для статей на портале)

- [ ] У значимых заметок есть тип по смыслу и заголовок; текст самодостаточен.
- [ ] Каты названы по содержимому; частые вопросы не спрятаны в каты.
- [ ] Каждый таб — законченный вариант инструкции.
- [ ] Нет HTML; вложенность интерактивных элементов — не глубже одного уровня.
- [ ] В собранном тексте нет недоподставленных переменных и неразрешённых условий (см. «Переменные и условия»).

### Автопроверки

- [ ] markdownlint-cli2 и Vale — ноль ошибок.
- [ ] Предпросмотр статьи на портале собран и просмотрен.

## 9. Разбор «было → стало»

Возьмём типовую статью базы знаний и перепишем её по правилам стайлгайда.

### 9.1. Было

```markdown
# Введение

Тут мы расскажем про пароли. Недавно мы обновили механизм входа.

## Про сброс

Если вы забыли пароль — его можно восстановить, см. выше, а также [здесь](https://docs.example.com/docs/console/password).

![](images/reset.png)

{% note info %}
Имена пользователей с точкой не поддерживаются.
{% endnote %}

{% cut "Подробнее" %}
Откройте страницу входа, нажмите «Забыли пароль?», введите логин и почту,
дождитесь письма, перейдите по ссылке и задайте новый пароль.
Ссылка живёт 24 часа.
{% endcut %}
```

### 9.2. Разбор проблем

1. Заголовок «Введение» не описывает содержание и не совпадает ни с каким вопросом пользователя (H1).
2. Лид «Тут мы расскажем про пароли» не содержит результата и ключевых слов (лид статьи).
3. «Недавно» — относительная дата, которая устарела в день публикации (даты и версии).
4. «См. выше» — ссылка на порядок чтения: в чанке она потеряна (самодостаточность).
5. Текст ссылки «здесь» не несёт смысла, ссылка абсолютная (ссылки).
6. Картинка без alt-текста: если на скриншоте есть шаги, для ассистента их нет (картинки).
7. Критичное ограничение спрятано в заметку без заголовка и с типом `info` вместо `warning` (заметки).
8. Единственная рабочая инструкция спрятана в кат с заголовком «Подробнее» — этот чанк не найдётся никогда (каты).
9. Нет front matter и FAQ: статья хуже фильтруется и не отвечает на частые вопросы (метаданные, частые вопросы).

### 9.3. Стало

```markdown
---
title: Как сбросить пароль в веб-консоли
description: Пошаговый сброс забытого пароля веб-консоли по ссылке из письма; ссылка действует 24 часа.
article_id: reset-console-password
product_area: console
tags:
  - пароль
  - вход
  - восстановление доступа
  - не могу войти
audience: user
status: active
updated_at: 2026-11-04
owner: Поддержка L2
---

# Как сбросить пароль в веб-консоли

Эта инструкция описывает, как сбросить забытый пароль веб-консоли
и восстановить доступ к аккаунту. Сброс занимает около пяти минут.

## Как сбросить пароль

1. Откройте страницу входа веб-консоли.
2. Нажмите **«Забыли пароль?»** под формой входа.
3. Введите логин и корпоративную почту, нажмите **«Отправить письмо»**.
4. Откройте письмо «Сброс пароля веб-консоли» и перейдите по ссылке
   в течение 24 часов: ссылка действует сутки с момента отправки.
5. Задайте новый пароль: не менее 12 символов, цифры,
   верхний и нижний регистр.

Если письмо не пришло в течение 15 минут — см. раздел
[Письмо со сбросом не приходит](email-not-received.md).

## Ограничения

{% note warning "Логины с точкой не поддерживаются" %}
Сброс пароля для логинов с точкой (например, `ivan.petrov`) не работает
с версии 2.3. Используйте вход через SSO: [Как войти через SSO](sso-login.md).
{% endnote %}

## Частые вопросы

### Сколько действует ссылка из письма?

Ссылка из письма действует 24 часа с момента отправки. Если ссылка
устарела, запросите новое письмо: повторите шаги раздела
«Как сбросить пароль».

### Куда обращаться, если сброс не помог?

Создайте заявку в поддержке: [Как создать заявку](create-ticket.md).
Укажите логин и время последней успешной попытки входа.
```

### 9.4. Ключевые изменения

1. H1 и `title` — полная формулировка задачи пользователя вместо «Введение».
2. Лид отвечает «что, для кого, сколько времени».
3. Инструкция вынесена из ката в основной текст, шаги — с результатами и сроками.
4. Критичное ограничение — заметка `warning` с заголовком, причиной и альтернативой (SSO).
5. Ссылки — осмысленный текст и относительные пути.
6. FAQ с вопросами в лексике пользователя и самодостаточными ответами.
7. Front matter с `tags` из лексики обращений; `description` содержит ключевой факт (24 часа).
8. Все сроки — абсолютные значения.

## 10. Шпаргалка

| Вопрос | Правило |
|---|---|
| Разделы | один тезис — один раздел; абзац — 2–4 предложения |
| Самодостаточность | без «см. выше»; факт повторяется там, где нужен |
| Заголовки | H1 = `title`; без скачков уровней; конспект из одних заголовков |
| Лексика | термины пользователя; один термин — одно понятие |
| Время | абсолютные даты и версии, числа с единицами |
| Метаданные | девять обязательных полей front matter |
| Списки | однородные; шаги инструкции — с ожидаемым результатом |
| Таблицы | подводка с выводом и полная шапка |
| Картинки | alt-текст обязателен; факты дублируются текстом |
| Ссылки | осмысленный текст, относительные пути |
| YFM-элементы | заголовок элемента — поисковый крючок; содержимое самодостаточно |
| Автопроверки | markdownlint + Vale; merge блокируется по `error` |

## 11. Глоссарий

- **RAG (retrieval-augmented generation)** — архитектура ассистента: поиск фрагментов по базе знаний плюс генерация ответа языковой моделью на их основе.
- **Чанк (chunk)** — фрагмент статьи, на который её режет пайплайн индексации; единица поиска и цитирования.
- **Эмбеддинг (embedding)** — векторное представление текста, по которому измеряется похожесть вопроса пользователя и чанка.
- **Retrieval** — этап поиска релевантных чанков в индексе перед генерацией ответа.
- **Индекс (векторное хранилище)** — база эмбеддингов всех чанков вместе с их метаданными.
- **Front matter** — YAML-блок метаданных в начале файла между строками `---`.
- **YFM (Yandex Flavored Markdown)** — диалект Markdown, который использует Diplodoc.
- **Diplodoc** — движок документации, собирающий портал из YFM-файлов.
- **MR (merge request)** — запрос на слияние ветки в git; форма ревью изменений.

Стайлгайд меняется через merge request в репозиторий стайлгайда; вопросы и предложения — редакторам команды документации. Для новых типов материалов (обучающие статьи, release notes) правила добавляются отдельными MR.
